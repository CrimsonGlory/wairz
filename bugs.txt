RESOLVED (2026-07-05): Full-suite-only backend test failures
==============================================================

Status: FIXED. Full suite (`pytest tests/`, 7092 collected) now runs
7037 passed, 54 skipped, 1 xfailed, 0 failed — confirmed by two
consecutive clean full-suite runs after the fixes below landed.

This document originally described 37 tests believed to share ONE root
cause (SQLAlchemy connection pool reused across pytest-asyncio's
per-test event loops). Root-causing each failure individually (rather
than trusting the original single-cause hypothesis) found that the 37
failures actually had THREE independent, unrelated causes. Only 3 of
the 37 were actually caused by the originally-diagnosed pool/loop
issue. Lesson: "fails only in the full suite" is a symptom shared by
several distinct classes of test-isolation bug, not a signature of any
one of them — don't stop root-causing at the first plausible theory
that fits the observed symptom.

Fix 1 — genuine cross-event-loop Postgres pool reuse (3 tests)
----------------------------------------------------------------
This is the ORIGINAL diagnosis below, and it was correct for the
subset of tests that go through the real Postgres engine via
`httpx.AsyncClient(transport=ASGITransport(app=app))` /
`TestClient` + `get_db` (router-level tests, not the SQLite
`make_live_db()` live-canary tests). `backend/app/database.py`
created `engine` as a module-level singleton with a real pooled
connection (`pool_size=15, max_overflow=25`). pytest-asyncio's
function-scoped event loop meant a pooled connection acquired under
test N's loop could be handed to test N+1 under a *different* loop,
and asyncpg raises "Task ... attached to a different loop" /
"cannot perform operation: another operation is in progress".

Fix: `backend/app/database.py` now detects `"pytest" in sys.modules`
and constructs `engine` with `poolclass=NullPool` under test (opens
and closes a fresh connection per checkout — no connection is ever
reused across loops). Production behavior (pool_size=15,
max_overflow=25, pool_recycle=3600) is unchanged when not running
under pytest.

Confirmed fixed: tests/test_ghidra_research_router.py::test_list_unknown_project_returns_404,
tests/test_terminal_router.py::test_websocket_terminal_accepts_query_param_key,
tests/test_rate_limit_tiers.py::test_dynamic_429_response_shape_on_security_audit.

Fix 2 — Alembic's fileConfig disabling every app-level logger (9 tests)
--------------------------------------------------------------------------
`backend/alembic/env.py` called `fileConfig(config.config_file_name)`
with Python logging's default `disable_existing_loggers=True`.
`tests/test_alembic_autogenerate_empty.py::test_alembic_autogenerate_is_empty`
calls `alembic.command.check(cfg)` IN-PROCESS (inside the same pytest
process as every other test, not as a separate CLI invocation).
`command.check` runs `alembic/env.py` via `script_directory.run_env()`,
which calls `fileConfig(...)`. Because `alembic.ini`'s `[loggers]`
section only lists `root, sqlalchemy, alembic`, `fileConfig`'s default
`disable_existing_loggers=True` sets `.disabled = True` on every OTHER
logger that already existed at that point (i.e. every `app.*` module
logger created via `logging.getLogger(__name__)` anywhere in the
codebase) — permanently, for the rest of the pytest process. Any later
test asserting on `caplog.records` for an app-level WARN/ERROR never
sees the record, because the logger producing it is disabled and never
propagates.

This has nothing to do with the DB connection pool or event loops —
it's a pure stdlib `logging.config.fileConfig` footgun for any
long-running process that invokes Alembic commands programmatically
(as opposed to Alembic's usual one-shot CLI invocation, where a
disabled logger doesn't matter because the process exits right after).

Fix: `backend/alembic/env.py` now calls
`fileConfig(config.config_file_name, disable_existing_loggers=False)`.
Harmless for the CLI-invoked case (migrator container running
`alembic upgrade head` in its own dedicated process, which never runs
another test needing those loggers afterward).

Fix 3 — a leaked raw-image-extension file poisoning detection-root
resolution for every later walker test (~25 tests)
------------------------------------------------------------------------
`tests/test_fs_extractors.py::test_symlink_escaping_sandbox` wrote a
permanent file — `tmp_path.parent / "outside.bin"` — directly into the
directory pytest tmp_path fixtures for ALL tests in the run share
(pytest's per-session basetemp, e.g. `/tmp/pytest-of-root/pytest-N/`).
The test never cleaned this file up (no `finally`, no `tmp_path`
scoping), so it persisted at the top level of the shared basetemp for
the rest of the pytest session — a real, permanent test-isolation bug,
independent of run order beyond "this test ran at some point earlier."

`app/services/firmware_paths.py`'s `_compute_roots_sync` has a
"shallow-container rescue" heuristic (see CLAUDE.md context on
`get_detection_roots`): when a firmware's `extracted_path` yields at
most one detection root AND that root's PARENT directory holds a raw
firmware image file directly at its top level (checked via
`_dir_has_raw_image`, a non-recursive, extension-only scan — `.bin`
included), the parent gets promoted into the detection-root list too.
This heuristic exists for real vendor-BSP shapes (Motorola scatter
extracts, Tegra L4T) where sibling firmware blobs sit one level above
the chosen extraction container — it is working exactly as designed.

The problem: any walker test built as
`Firmware(extracted_path=str(tmp_path), ...)` + `get_detection_roots()`
has `tmp_path`'s own parent equal to the SAME shared pytest basetemp
that `test_fs_extractors.py` polluted. Once that one `outside.bin` file
existed anywhere in the basetemp, `_dir_has_raw_image(basetemp)`
returned True for every subsequent tmp_path-based walker test in the
session, promoting the ENTIRE shared basetemp into that test's
detection roots — so the walker's `os.walk` swept every sibling test's
own tmp_path subdirectory too, picking up whatever real fixture files
those OTHER, unrelated tests had written for their own purposes. Result:
file/entry counts inflated by however many prior sibling tmp_path dirs
happened to contain matching content by the time each test ran — which
explains why the counts grew through the run and why isolated/small
batches never reproduced it (few or no sibling dirs exist yet).

Confirmed via bisection: `pytest tests/test_fs_extractors.py
tests/test_journald_walker.py` alone reproduced
`assert result["files_scanned"] == 1` failing with `6` instead — with
no other files in the run at all.

Fix: `tests/test_fs_extractors.py::test_symlink_escaping_sandbox` now
nests the "outside" fixture inside its own uniquely-named subdirectory
(`tmp_path.parent / f"outside-{uuid.uuid4().hex[:8]}"`, `.mkdir()`, then
the `.bin` file inside that), matching the existing safe pattern
already used by `test_python_ast_walker.py`,
`test_prefetch_walker.py`, `test_srum_walker.py`, and
`test_scheduled_task_walker.py`'s own "escape symlink" tests.
`_dir_has_raw_image` only scans direct file children (not directories),
so a raw-extension file nested one level deeper no longer trips the
heuristic. The test's actual intent (symlink target genuinely outside
the sandboxed `tmp_path`) is unchanged.

A related, already-safe case: `test_find_filesystem_root.py`'s
`test_symlink_to_fs_image_not_followed` also writes to
`tmp_path.parent / "outside.img"`, but wraps it in
`try/finally: outside.unlink(missing_ok=True)` — genuinely transient,
not a permanent leak, left as-is.

Original diagnosis (superseded by the above — kept for history)
=================================================================
Known-flaky backend tests (2026-07-05)
Root cause (partial — see Fix 1 above; did NOT explain 34/37 failures)
----------------------------------------------------------------------
backend/app/database.py creates `engine` (a SQLAlchemy async engine with
a real connection pool, pool_size=15) as a MODULE-LEVEL SINGLETON at
import time. This matches production, where uvicorn's single event loop
lives for the whole process lifetime.

pytest-asyncio's default (function-scoped) event loop gives every test
function its OWN new event loop. When a router test acquires a real
Postgres connection from the shared pool under test N's loop, and a
later test tries to reuse that same pooled connection under test N+1's
(different) loop, asyncpg refuses the cross-loop reuse.

The three "variants" originally described here (dangling background
tasks producing cosmetic "coroutine was never awaited" warnings, and
the WebSocket BlockingPortal thread-loop case) are real but were,
on closer inspection, either cosmetic (the coroutine warnings) or
already covered by Fix 1 (the WebSocket case, terminal_router).
