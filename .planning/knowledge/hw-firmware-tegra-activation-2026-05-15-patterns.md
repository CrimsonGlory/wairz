### 1. Recursive NVD-CPE verification extends to chipset_regex ENUMERATED VALUES (6 sessions running)
- **Description:** The morning session established that NVD-CPE verification applies to user prompts + scout reports + reviewer findings + CVSS field values. This session EXTENDED the discipline to chipset_regex ENUMERATED VALUES — every value in the regex needs NVD-CPE provenance, not just the regex's general SCOPE. Reviewer B caught CVE-2017-18159 chipset_regex over-broad inclusion of post-2018 Snapdragon codenames (bengal/kona/lahaina/waipio/niobe/sun/magpie/moorea/saipan) that POST-DATE the 2018-06-05 CAF patch — these would over-attribute on 2020+ XBL blobs that NVD does NOT list as affected.
- **Evidence:** 8 independent NVD WebFetches this session (1 implementer-side + 7 Reviewer-B-side); 1 CRITICAL chipset_regex drift caught + fixed via tightening to NVD-faithful 2018-cohort prefixes only `(?i)^(msm|mdm|qm[0-9]|sdm[0-9]{3}|sd[0-9]{3}|sda[0-9]{3})`.
- **Applies when:** Any session pinning a CVE attribution with a chipset_regex narrowing. The regex CONTENTS (not just the regex shape) need per-value NVD-CPE provenance. **Cross-reference:** CVE-2019-5680 (R32.3.1+ misattribution caught morning session), CVE-2017-18159 (chipset_regex contents over-broad caught this session) — both follow the same recursive-discipline-failure pattern.

### 2. Pre-implementation width-canary audit (Rule #31) prevents migration scope explosions
- **Description:** When activating a destructive change (like a schema gate that SKIPS non-conforming entries), audit the entire migration scope BEFORE landing the change. A single SQL `COUNT(*)` (~1 second) reveals whether the user-prompt's named entries are the full scope or just one instance of a broader pattern. The F-FORENSIC-10 gate's user prompt named only CVE-2017-18159 needing pre-narrowing; the audit revealed 16 entries (15 additional) at risk — would have silently dropped ~5,000 CVE rows on next cve-match.
- **Evidence:** Pre-implementation `SELECT cve_id, COUNT(*) FROM sbom_vulnerabilities WHERE cve_id IN (...) GROUP BY cve_id` revealed 22 of 25 audited CVEs firing with 5,000+ blob rows. Pre-narrowed all 16 entries before gate activation. Post-implementation regression check: BRAKTOOTH baseline 54 rows + CVE-2017-18159 147 rows + 0 wrong-attribution — all preserved.
- **Applies when:** Activating any destructive schema change. The user prompt's named scope is a CANDIDATE; the database truth is the full scope. Pre-implementation audit costs ~1 second and eliminates regression risk.

### 4. Multi-stage fallback chain (content-first → path-inference → magic-bypass-with-context-gate)
- **Description:** When a primary extraction path (e.g. blob-content scan for a banner string) doesn't cover the entire real corpus shape, layer fallbacks in order of evidence quality: (1) content scan (most authoritative — Rule #19 evidence-first), (2) path inference (cheap fallback when content is unavailable), (3) magic-bypass with context-gate (covers deferred-TBD subsets). Each layer has its own positive + negative tests. Precedence is content > path (content-banner-wins-over-path-inference Rule #19 canary asserts this).
- **Evidence:** Commits `f54d415` + `0a901f2` + `338f95b` implement the 3-stage chain. 35 paired-canary tests verify each stage's positive + negative cases + the precedence rule. End-to-end DS1 result: 63 of 99 blobs receive l4t_release (vs 0 without the chain).
- **Applies when:** Designing extraction for a field that may live in multiple forms (inline content, path encoding, filename pattern, sibling-file presence). Layer fallbacks; gate aggressive fallbacks with context checks to prevent false-positives.

### 5. Per-component path-context gate prevents whole-path-substring false-positives
- **Description:** When using path substring matching for heuristic attribution, scope the check to the path SEGMENT containing the signal — not the whole path. Whole-path substring matches surface false-positives when an UPSTREAM path component contains the gate token unrelated to the signal-bearing component. pytest tmp paths like `/tmp/pytest/test_l4t_release/MyProject_R32.3.1_backup/` contain "l4t" in the test name far from the version-bearing component — whole-path match returned True; per-component match returns False.
- **Evidence:** `_has_tegra_path_context()` initially used whole-path substring; failed pytest. Switched to per-component check (only the path component containing R<N>.<x>.<y> match counts) — pytest tmp paths handled correctly.
- **Applies when:** Any path-based heuristic gate. The path is a multi-segment structure; scope checks to the relevant segment. Generalises Rule #46 (paired-canary) — the per-component check IS the canary's positive shape; whole-path matching would have silently broken under realistic file system layouts.

### 6. state_snapshot() public method as abstraction-boundary fix; defensive getattr was the mask
- **Description:** Replacing private-attr access via `getattr(loader, "_field", None)` with a public state_snapshot() method removes the silent-masking behavior. The defensive shape returned None on missing attrs without exception — any future rename of `_cached_mtime_ns` → `_atomic_mtime` would have silently produced `yaml_mtime_iso=null/status=defaults` with no exception. The public method forces an AttributeError on any class-shape change — refactor signals now surface as load-bearing errors.
- **Evidence:** Commit `bbaef3b` shipped 8-key stable contract dict from `state_snapshot()` + 9 new tests including Rule #46 META-CANARY asserting the public method exists on the loader (`test_surface_state_payload_no_private_attr_access_required`). Grep confirms zero external `_cached_mtime_ns` / `_loaded_from_yaml` accesses outside yaml_cache.py post-refactor.
- **Applies when:** Any abstraction-boundary violation where a consumer reads private attrs of a class. Add a public state-snapshot method; remove the defensive getattr; ship a Rule #46 META-CANARY asserting the contract.

### 8. Minimum-impact ceremonial narrowing satisfies a schema gate without behavior change
- **Description:** For YAML entries whose NVD-CPE scope doesn't enumerate further than vendor+category (framework-level CVEs like Bluedroid, binary-level CVEs like wpa_supplicant), satisfy the F-FORENSIC-10 gate via `category_regex: ^<existing_category>$`. Preserves exact-match semantics (the matcher uses case-insensitive `re.search` — anchored regex matches the existing exact-match value). Satisfies the gate's narrowing-field-presence check. Documents the deferred work via inline YAML comments referencing the genuine NVD-derived narrowing follow-up.
- **Evidence:** Commit `5398f16` applied this pattern to 14 of 16 pre-narrowed entries. Regression check: all 14 entries preserved their currently-firing rows (FragAttacks 1176 × 4 firmwares, MediaTek modem 20 × 3 firmwares, wpa_supplicant 36-38 × 3-4 firmwares, etc.).
- **Applies when:** A schema gate requires "narrowing field set" but the entry's NVD scope is genuinely at the vendor+category level (no further enumeration). Ceremonial narrowing satisfies the gate + preserves behavior + documents the deferred genuine-narrowing work. **Anti-pattern to avoid:** treating ceremonial narrowing as a cargo-cult substitute for genuine NVD-derived narrowing on entries where the latter IS available.

### 9. on_conflict_do_nothing detector behavior — existing rows aren't updated on re-detect
- **Description:** The detector uses `stmt.on_conflict_do_nothing(constraint="uq_hwfw_firmware_sha256")` — when re-detecting an existing firmware, blob rows whose `(firmware_id, blob_sha256)` already exist are SKIPPED. For verifying that a parser-output change (new metadata field) takes effect on already-detected firmware, DELETE the existing blob rows FIRST + re-run detection. Documented Pattern #9 from this session — saves debugging time when "did this code change affect output?" questions arise.
- **Evidence:** Caught mid-session: initial re-detect after L4T extraction landing returned "99 blobs detected" but SQL showed 0 blobs with `metadata->>'l4t_release'`. `on_conflict_do_nothing` was the cause. `DELETE FROM hardware_firmware_blobs WHERE firmware_id = '...'` + re-detect → 63 blobs with l4t_release populated.
- **Applies when:** Verifying any parser-output / classifier-output change on previously-detected firmware. Document the DELETE-then-redetect step in test plans; consider whether parser-output backfill needs a one-shot SQL UPDATE for the existing corpus OR a deliberate detector behavior change.
