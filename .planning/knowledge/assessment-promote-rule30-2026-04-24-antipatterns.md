## Failed Patterns

### 1. Trusting the seed's named carve-out target without re-verification
- **What was done:** The seed `.planning/intake/seed-next-session-2026-04-24.md` (written by session 0801ca27 on 2026-04-23) proposed Route A as "carve out the P3 circular imports" and specifically listed `security_audit_service ↔ assessment_service` as the TOP candidate pair: "14 imports, existing `security_audit_service.run_scan_subset` as the extract point." My first-pass response recommended executing against that pair.
- **Failure mode:** `security_audit_service.py` was **deleted in Phase 5 part 2** (session b56eb487, 2026-04-21) — 2 days BEFORE the seed was written, 3 days BEFORE this session. Its existence in the seed is a ghost. Harness rule `from app\.services\.security_audit_service\b` (in `.claude/harness.json` qualityRules.custom) now flags any code that references the deleted name. Blindly executing the seed's recommendation would have tripped the harness rule, confused the session, and wasted a dispatch budget on a pair that no longer has a cycle (or a pair, since one half is deleted).
- **Evidence:** Session Step 2 grep: `security_audit_service.py` not present under `backend/app/services/`; harness rule id `[NO-ID]` with pattern `from app\.services\.security_audit_service\b` and message "Learned from campaign wairz-intake-sweep-2026-04-19 session b56eb487: security_audit_service.py was deleted in Phase 5 part 2 split."
- **How to avoid:** Before executing any seed's named target, grep for the named entity: `ls backend/app/services/<named_file>.py` or `grep -rn "class <NamedClass>" backend/`. Seeds capture intent at write-time; the code's truth is at execute-time. Rule #19 evidence-first applies to seeds, not just intakes. This is the third seed-staleness incident in 2 weeks (after Rule #28's 14-22% LOC drift and Rule #25's sub-task miscounts); consider making "re-verify seed's named entities" a harness rule of its own if the pattern recurs.

### 2. Two-defect stackup hiding `_phase_compliance` dead code for weeks
- **What was done:** `assessment_service.py` had two defects layered on top of each other. **Defect 1:** `async def _phase_compliance(self)` contained `from app.services.compliance_service import ComplianceService` but the class in that module was renamed to `ETSIComplianceService` (no compat alias). Lazy-import defers the ImportError from module-load time to phase-invocation time. **Defect 2:** The outer phase runner in `run_assessment()` wraps every phase call in `try: await phase_func() except Exception: ...` that logs the exception but does NOT re-raise — the next phase continues. ETSI EN 303 645 compliance has been producing zero findings on every assessment run since the rename (unknown exact date — weeks to months).
- **Failure mode:** Either defect alone would have been caught. Defect 1 alone: at module-import time, pytest collection would fail. Defect 2 alone: phase runs (even with latent import bugs) would surface in test failures IF the phase had tests. Stacked, the phase silently returns 0, the summary finding isn't generated, the report's compliance section is empty, and no alarm ever rings. NO TESTS cover `_phase_compliance` (`grep -rln "_phase_compliance\|ComplianceService" backend/tests/` returned **0 hits**) — which is the third defect that let the first two persist.
- **Evidence:** Commit `fc384bb` message; runtime import smoke output `ImportError: cannot import name 'ComplianceService' from 'app.services.compliance_service'. Did you mean: 'ETSIComplianceService'?`; phase-runner code at `assessment_service.py:158` + surrounding `try/except` wrapper.
- **How to avoid:**
  1. **Prefer top-level imports** so import errors surface at startup (Rule #30 default: promote when no legitimate-lazy reason applies).
  2. **Phase-wrapper try/except must log `exc_info=True` AT MINIMUM** so stale-symbol errors are discoverable in logs. Better: add a first-run smoke (`if phase_idx == 0: try: phase_func() except: raise`) to fail loud on structural problems.
  3. **Every phase registered in a phase list MUST have a test** — even a single test that asserts `phase_func()` doesn't raise on empty fixtures. This would have caught both defects. Candidate intake: audit every `phases = [...]` list in the codebase against `tests/` coverage.
  4. **Rename discipline:** when renaming a class, grep for the OLD name across `backend/app/` AND `backend/tests/` before committing — a companion-to-Rule #9 (frontend Record<> exhaustiveness) but for Python renames.

### 3. Manufactured-work temptation when the intake queue is empty
- **What was done:** The seed's own "Risk" section warned: "Temptation to fabricate work: intake queue being empty is a GOOD state. Resist inventing campaigns 'because autopilot ran dry.' Maintenance options (C) are legitimate; manufactured features are not." During initial route scoring it was tempting to propose a large "P3 full sweep across all 13 files" campaign as the "biggest ship" option.
- **Failure mode:** A mechanical sweep of all 37 function-locals across all 13 files would have hit Rule #30 legitimate-lazy cases (e.g. any file that lazy-imports androguard primitives directly, any wrapper that lazy-imports yara for C-extension fast-paths). Without per-file analysis, promotion would have either (a) broken production (androguard cold-import at startup ≈ 500 ms × every backend request path) or (b) leaked LGPL into the module graph. Beyond correctness: a sweep-campaign manufactured from "no pending work" is Rule #19's "dead abstraction" shape — it exists because capacity existed, not because evidence demanded it.
- **Evidence:** Seed file `.planning/intake/seed-next-session-2026-04-24.md` §Risk; the session's own route-scoring where Route B (wait) was ranked legitimate-but-null; this session's assessment_service audit (which found 2/10 imports would have required per-target verification anyway, confirming sweep was unsafe).
- **How to avoid:** When autopilot reports empty, reframe the question from "what campaign should I start" to "what PENDING OBLIGATION exists." Obligations are durable: Rule #21 sync, untracked-but-useful files, broken invariants, latent bugs discovered but not yet fixed. Features/refactors are not obligations unless evidence (a bug, a latency complaint, a failing test) demands them. This session: C had three concrete obligations (untracked vendor-aes, Rule #30 candidate, Rule #21 mirror), A was a scoped-cleanup that happened to surface a bug. Neither was manufactured; both had a claim on the session before it started.

### 4. Grep-only cycle audit without explicit acknowledgment that it's first-order
- **What was done:** First-pass cycle analysis ran `grep -rn "from app\.services\.assessment_service" backend/app/services/<callee>*` for each of 9 callees and concluded "0 back-imports = cycle-free." The conclusion was technically correct for THIS session's promotion (smoke passed), but the analysis method was incomplete on its own terms: it did not check transitive cycles (`sbom → X → Y → assessment_service`). For this specific case, the forward grep also showed 8/10 callees were already top-level-imported elsewhere — meaning they'd ALREADY been pulled into the import graph at app startup WITHOUT creating cycles — so transitive cycles through them were provably not an issue. But that reasoning was implicit rather than stated.
- **Failure mode:** Had I promoted imports in a service whose callees were NOT already top-level-imported elsewhere (e.g. a newly-created service or a truly-isolated subtree), grep-only audit would have missed 2-hop cycles, the smoke would have caught it, but the narrative around "cycle-free" would have been misleading. Same grep → different context → different confidence. The anti-pattern is claiming confidence that the method doesn't warrant.
- **Evidence:** The session transcript's claim "all 9 callees have 0 back-imports → no cycle risk" appears without the caveat that it's first-order only; only the runtime smoke provides transitive-cycle guarantees.
- **How to avoid:** When communicating "cycle-free" to the user / next session, pair the claim with method: "grep first-order clean (0 back-imports in 9 callees); runtime smoke confirms no transitive cycles." The two together are load-bearing; either alone is not. Companion to Rule #17 canary discipline: any verification step has a scope limit; state it.

### 5. Under-counted function-local removal delta (model + cross-layer imports not in the `from app.services.*` grep)
- **What was done:** Pre-execution audit said "10 function-local service imports in assessment_service." Execution actually promoted **13**: 10 services + 1 `from app.ai.tools.binary import _scan_all_binary_protections` (cross-layer, counted separately) + 2 `from app.models.firmware import Firmware` duplicates (counted as "model" not "service"). The codebase-wide delta was reported as "-11" because the grep filter was `from app\.services\.*` only — the `app.ai.tools.binary` promotion didn't show up in the before/after count even though it was real work.
- **Failure mode:** Metrics drift between count-audits and change-scope; under-counting makes "did we catch everything?" verification fragile. In this case the smoke caught everything anyway, but on a larger sweep the gap would matter (is the remaining 26 the whole story? or is it 26 `from app.services.*` + unknown other cross-layer?).
- **Evidence:** Grep pattern `^\s*from app\.services\.` used session-wide; `app.ai.tools` and `app.models` not included; intake housekeeping commit `565c9d7` reported "-11" as if that were the full delta.
- **How to avoid:** When auditing function-local imports, use the broadest pattern: `^\s{4,}from app\.` (any indented `from app.` catches services + models + ai + schemas + workers). Report the full delta. If splitting by category helps, provide both: "overall -13 function-locals (10 services, 1 cross-layer ai, 2 models)."
