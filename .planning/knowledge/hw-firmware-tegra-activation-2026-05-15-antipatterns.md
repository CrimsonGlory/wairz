## Failed Patterns

### 1. Deriving chipset_regex CONTENTS from intuition about vendor naming families (rather than from NVD CPE evidence)
- **What was done:** The initial CVE-2017-18159 chipset_regex landing (`5398f16`) used `(?i)^(msm|mdm|sdm|sda|sd[0-9]|sm[0-9]|sa[0-9]|qcs|qcm|qm[0-9]|sdx|snapdragon|bengal|kona|lahaina|waipio|niobe|holi|sun|magpie|moorea|saipan)` — derived from intuition about Qualcomm Snapdragon naming families. The implementer-side WebFetch DID run on the NVD CPE; the regex was intended to match the NVD description scope ("Android for MSM, QRD Android, Firefox OS for MSM"). But the regex INCLUDED post-2018 Snapdragon codenames (bengal/kona/lahaina/waipio/niobe/sun/magpie/moorea/saipan) — codenames that POST-DATE the 2018-06-05 CAF patch.
- **Failure mode:** Over-attribution on 2020+ Snapdragon firmware. CVE-2017-18159 affects ABL/SBL code shipped in CAF kernels through June 2018; modern XBL/SBL1 blobs shipping Bengal (2020) or Kona (Snapdragon 865, 2019) chipsets are NOT in NVD scope. The over-broad regex would attribute CVE-2017-18159 to those modern blobs, producing forensically-incorrect rows.
- **Evidence:** Reviewer B forensic-domain review independently re-fetched the NVD CPE; flagged the post-2018 codename inclusion. NVD CPE for CVE-2017-18159 lists ONLY `cpe:2.3:o:google:android:-:*` (no specific Snapdragon SoCs enumerated). Description scope is the 2018 CAF MSM cohort, not modern Snapdragon.
- **How to avoid:** The recursive NVD-CPE verification discipline extends to chipset_regex ENUMERATED VALUES, not just the regex's general scope. Every VALUE in the regex needs NVD-CPE provenance — if NVD doesn't enumerate "kona" / "bengal" / "waipio", these values DON'T belong in the regex. The implementer-side WebFetch caught some drifts (the 14 minimum-impact narrowings were correctly chosen for vendor+category-only NVD scope); the reviewer-side WebFetch caught the chipset_regex contents drift. **Triple-verification (scout → implementer → reviewer) caught what single-axis verification missed.**

### 2. Activating a destructive schema change without pre-implementation width-canary audit of migration scope
- **What was done:** The user prompt's TARGET 2 spec named CVE-2017-18159 as the entry needing pre-narrowing before adding the F-FORENSIC-10 gate ("otherwise the gate silently excludes a CVE that has been firing"). Implementing this verbatim would have shipped the gate + the CVE-2017-18159 narrowing — and the gate would have SILENTLY REJECTED 15 OTHER currently-firing CVE-bearing entries (FragAttacks / MediaTek modem×3 / MediaTek DA OOB / 5 Bluedroid / 4 wpa_supplicant) totaling 5,000+ CVE rows that would have silently disappeared on next cve-match.
- **Failure mode:** Mass regression on the corpus. BRAKTOOTH baseline (54 rows) would have been preserved (it has chipset_regex narrowing already), but the FragAttacks 3528 rows + MediaTek modem 60+ rows + wpa_supplicant 147 rows + Bluedroid potential firings would all silently vanish.
- **Evidence:** Pre-implementation audit (1 SQL query, ~1 second) — `SELECT cve_id, COUNT(*) FROM sbom_vulnerabilities WHERE cve_id IN (...) GROUP BY cve_id` revealed 22 of 25 audited CVEs firing. The audit was triggered by my recognizing the user prompt's principle — "otherwise the gate silently excludes a CVE that has been firing" — applies to ALL entries the gate might reject, not just the one named.
- **How to avoid:** Per Rule #31 width-canary: before activating a destructive schema change, audit the FULL migration scope. The user prompt's named scope is a CANDIDATE; the database truth is the full scope. Cost: 1 second per pre-implementation audit. Value: prevents regression on 5,000+ rows. **The user's principle applies to ALL impacted entries, not just the one named.**

### 3. Shipping a parser fix that fits the canonical case but not the real corpus shape
- **What was done:** TARGET 1 (`f54d415`) implemented L4T release extraction by scanning blob HEAD BYTES for the `/etc/nv_tegra_release` banner. All 28 unit tests passed (canonical R32/R28/R35/R36 cases + bare/comment-prefixed variants). Real-corpus end-to-end test on DS1 returned 0 blobs with `l4t_release` populated — the DS1 corpus is operator-renamed standalone bootloader/DTB/MCU blobs that don't carry the banner inline.
- **Failure mode:** The forward-prepared CVE pins (the WHOLE POINT of TARGET 1) would have remained silently dormant despite the L4T extraction code shipping. Operator-invisible regression — the parser "works" per unit tests but doesn't activate the pins per end-to-end verification.
- **Evidence:** SQL query post-re-detect: `SELECT metadata->>'l4t_release' AS l4t, COUNT(*) FROM hardware_firmware_blobs WHERE firmware_id = '...' GROUP BY 1` returned only `(NULL, 99)`. Investigation: DS1's `data.dataimg` is raw_bin (134MB, the rootfs container), and the BSP-archive directory `L4T_BSP_SecureBoot.R32.3.1.tar.gz_extracted/` is unpacked but the canonical `/etc/nv_tegra_release` text file isn't a magic-byte-recognizable blob.
- **How to avoid:** Per Rule #19 evidence-first + Pattern #4 from morning session: end-to-end real-corpus verification BEFORE trusting that a parser change activates the dependent feature. Unit tests catch the function shape; real corpus catches the corpus-shape fit. Budget for N follow-up commits per Rule #25 — incremental gap closure via path-inference fallback + raw_bin 5th fallback delivered the activation. **"All tests pass" is not equivalent to "the feature is activated"** — verify against real corpus, not just synthetic fixtures.

### 4. Gating fallback on magic-byte subset detection when the corpus is dominated by the deferred-TBD subsets
- **What was done:** Activation-gap fixup #1 (`0a901f2`) added path-inference fallback inside the 4 subset parsers (`_parse_tegra_elf` / `_parse_tegra_fdt` / `_parse_tegra_android_bootimg`). cve-match on DS1 returned 0 matches despite 39 blobs receiving `l4t_release=R32.3.1`.
- **Failure mode:** The 39 L4T-tagged blobs were all `category: dtb` (FDT subset). The 6 forward-prepared Tegra CVE pins require `category: bootloader` or `category: tee`. DS1's bootloader/TEE blobs are NVIDIA-wrapper raw_bin format — magic doesn't match any of the 4 in-scope subsets, so `parse_tegra_blob` returns None and path-inference never runs.
- **Evidence:** Category breakdown: 39 L4T-tagged blobs all `dtb`; the 21 bootloader + 6 TEE blobs have no `l4t_release`. The NVIDIA wrapper magic + BUP container magic are deferred TBDs in the parser — they make up a large fraction of the DS1 corpus.
- **How to avoid:** When the deferred-TBD subsets are a large fraction of the real corpus, the fallback path must survive the magic-byte miss. Activation-gap fixup #2 (`338f95b`) added 5th magic-byte-bypass fallback gated on Tegra/L4T context tokens (l4t / tegra / jetson / bpmp / cboot / nvtboot) in the path. Per-component context gate prevents whole-path false-positives. **Don't gate aggressive fallbacks on the same shape that's failing** — the magic-byte miss is precisely the case the fallback must cover.

### 5. Whole-path substring matching for path-context gates (vs per-component check)
- **What was done:** Initial implementation of `_has_tegra_path_context()` used whole-path substring match (`token in path.lower()`). Failed pytest negative canary because pytest tmp paths like `/tmp/pytest/test_l4t_release_5th_fallback/MyProject_R32.3.1_backup/random.bin` contain "l4t" in the test name far from the version-bearing component.
- **Failure mode:** Whole-path substring would attribute `l4t_release` to ANY blob in a tmp path containing "l4t" in any upstream component — including completely unrelated non-Tegra blobs. Test name itself triggered the false-positive.
- **Evidence:** Test failure: `ParsedBlob(metadata={'l4t_release': 'R32.3.1'})` instead of `None` for a path with "l4t" in test name but no Tegra context in the release-bearing component.
- **How to avoid:** Scope path-context checks to the SEGMENT containing the signal. Per-component check (only the path component containing R<N>.<x>.<y> match counts) eliminates upstream-component noise. Generalises to any path-based heuristic — the path is multi-segment; scope checks to the relevant segment, not whole path.

### 6. Defensive getattr() on private attrs that masks refactor signals
- **What was done:** The old `_surface_state_payload` in `tools/hardware_firmware.py` read 4 private attrs of `MtimeCachedYamlLoader` via defensive `getattr(loader, "_field", None)` calls. The defensive shape silently returned None on missing attrs without exception.
- **Failure mode:** Any future rename (e.g. `_cached_mtime_ns` → `_atomic_mtime` for an mmap variant) would silently surface as `yaml_mtime_iso=null/status=defaults` in MCP `list_extension_points` output. Operator-invisible regression — the tool returns "everything looks fine (defaults)" when the loader's actually loaded from YAML.
- **Evidence:** Reviewer A A6+A7 from morning session flagged this as deferred work. This session shipped the fix (commit `bbaef3b`) — replaced with public `state_snapshot()` method that raises AttributeError on any class-shape change, surfacing refactor signals as load-bearing errors.
- **How to avoid:** Don't use defensive `getattr(obj, "_field", None)` for cross-module private-attr access. Add a public method on the class; consumers call the public method. Rule #46 META-CANARY (`test_surface_state_payload_no_private_attr_access_required`) asserts the public contract exists — prevents future re-introduction of the defensive shape.

### 7. Re-running detect_hardware_firmware on an already-detected firmware to verify a parser-output change
- **What was done:** After landing the L4T extraction enhancement, ran `detect_hardware_firmware(DS1_ID, db)` + commit. Function returned "99 blobs" but SQL query showed 0 blobs with `metadata['l4t_release']`. Initially confused about which level was failing.
- **Failure mode:** `on_conflict_do_nothing(constraint="uq_hwfw_firmware_sha256")` in the detector means existing `(firmware_id, blob_sha256)` rows are SKIPPED on re-detect. The detection LOGIC ran on 99 candidates, but the INSERT was no-op because rows already existed at the previous metadata snapshot.
- **Evidence:** Caught via metadata SQL query returning 0 hits despite "detected 99 blobs" output. Fix: `DELETE FROM hardware_firmware_blobs WHERE firmware_id = '...'` + re-detect → 63 blobs with new metadata.
- **How to avoid:** When verifying parser-output / classifier-output changes on already-detected firmware, DELETE existing blob rows before re-detection. Document the DELETE step in test plans. Consider whether parser-output backfill needs a one-shot SQL UPDATE OR a detector behavior change.

### 8. Initial state_snapshot summary-raises canary triggered the load-time exception path
- **What was done:** Initial test for `state_snapshot()`'s defensive try-except around `_summary(cached_value)` passed a raising summary callable to the loader constructor. The success-path INFO log in `_reload()` ALSO calls `_summary(parsed)` — the exception propagated from `loader.get()`, not from `state_snapshot()`.
- **Failure mode:** Test failed with RuntimeError instead of asserting the defensive fallback. The test was structurally wrong — it tested whether the load handshake survives a raising summary (it doesn't), not whether state_snapshot's defensive try-except works.
- **Evidence:** `RuntimeError: summary boom` raised from `loader.get()` during the success-path INFO log.
- **How to avoid:** When testing a defensive try-except, the fixture must isolate the exception path to the code under test. Updated test uses working summary at load time, then swaps `loader._summary` to the raising callable BEFORE calling `state_snapshot()`. **Test fixtures must reproduce the exact failure condition the defensive code is on — not a different condition that triggers a different exception path.**

### 9. Initial L4T release path-inference regex word-boundary anchors that fail on underscore-separated paths
- **What was done:** Initial path-inference regex used `\b` word-boundary anchors: `\bR(\d{2,3})\.(\d+)\.(\d+)\b|\bR(\d{2,3})\.(\d+)\b`. Failed on path `Tegra210_Linux_R28.2_aarch64` because `_` IS a word character in Python regex — `\b` between `_` and `R` requires a word/non-word transition, but both are word chars.
- **Failure mode:** Real-world L4T BSP paths use underscore separators. The `\b` anchor fails silently — regex returns None even though "R28.2" IS in the path.
- **Evidence:** Test failure: `test_l4t_release_path_inference_handles_major_minor_only` returned None instead of "R28.2".
- **How to avoid:** Use lookarounds (`(?<![A-Za-z0-9])` for start, `(?!\.?\d)` for end) instead of `\b` when the path may be underscore-separated. The character class `[A-Za-z0-9]` excludes `_` from the "preceding alphanumeric" check, allowing the match to start after an underscore.

### 10. Treating ceremonial narrowing as a substitute for genuine NVD-derived narrowing
- **What was done:** 14 of 16 pre-narrowed YAML entries received `category_regex: ^<existing_category>$` (e.g. `category_regex: ^modem$` when `category: modem` already exists). The regex doesn't add NEW narrowing — it re-encodes the same exact-match constraint via a regex. Satisfies the F-FORENSIC-10 gate's narrowing-field-presence check syntactically; doesn't satisfy the gate's INTENT (prevent disclosure-batch over-attribution).
- **Failure mode:** Future contributors who see `category_regex: ^modem$` paired with `category: modem` may treat this as the BLESSED narrowing pattern and apply it to entries where genuine NVD-derived narrowing IS available — silently growing the cargo-cult ceremonial-narrowing surface.
- **Evidence:** Reviewer C MEDIUM finding flagged this risk. The 14 entries' YAML comments now reference "Future enhancement: per-NVD-derived chipset_regex / version_regex per recursive verification discipline" to clearly mark them as deferred work, not as the canonical shape.
- **How to avoid:** Ceremonial narrowing is acceptable as a TEMPORARY pre-narrowing pattern when genuine NVD scope is at vendor+category level OR when the NVD evidence requires extraction infrastructure not yet shipped (e.g. modem-version-banner parsing). Document each ceremonial narrowing's deferred-work follow-up inline + in postmortem. **Don't ship ceremonial narrowing as the canonical pattern for entries where genuine narrowing IS available.**

## Cross-Cutting Anti-pattern Themes

1. **"NVD CPE describes the ATTRIBUTION; the regex must match the ATTRIBUTION."** This session's CVE-2017-18159 over-broad chipset_regex was an intuition-derived superset of the NVD attribution scope. Every value in a regex needs NVD provenance. Reviewer B catches the drift by independently re-deriving the regex from the same NVD URL.

2. **"Unit tests catch function shape; real corpus catches corpus-shape fit."** TARGET 1's canonical L4T extraction passed 28 tests but activated 0 pins on DS1. Real-corpus verification surfaced 2 activation gaps requiring fixup commits. Budget for N follow-up commits when corpus shape can diverge from canonical case.

3. **"The user prompt's named scope is a CANDIDATE; the database truth is the full scope."** The F-FORENSIC-10 gate would have silently dropped 15 additional entries the user prompt didn't name. Pre-implementation width-canary audit (~1 second) prevents this regression.

4. **"Don't gate fallbacks on the same shape that's failing."** Path-inference inside the 4 subset parsers didn't help raw_bin Tegra wrappers because the magic-byte miss IS the failure mode. The 5th magic-byte-bypass fallback covers this — but its own gate (per-component context) prevents false-positives in unrelated paths.

5. **"Defensive getattr() is a refactor-signal mask."** `getattr(loader, "_field", None)` silently returns None on missing attrs. A future rename produces operator-invisible regression. Public methods + Rule #46 META-CANARIES force refactor signals to surface as load-bearing errors.

6. **"on_conflict_do_nothing means existing rows aren't updated on re-detect."** Verifying parser-output changes requires DELETE + re-detect, not just re-detect. Documented as Pattern #9 from this session.

7. **"`\b` word-boundary anchors fail on underscore-separated paths because `_` IS a word char."** Use `(?<![A-Za-z0-9])` lookarounds for path-segment regex matching.

8. **"Ceremonial narrowing must be documented as deferred work, not enshrined as canonical."** The 14 minimum-impact `category_regex: ^<existing>$` narrowings preserve behavior + satisfy gate but don't add genuine narrowing. Inline YAML comments reference the genuine-narrowing follow-up; CLAUDE.md note (Reviewer C MEDIUM) would explain WHEN ceremonial vs genuine is appropriate.

9. **"Multi-persona reviewer dispatch catches drift that single-axis verification misses — 6 sessions running."** Reviewer B's independent NVD WebFetch caught what the implementer-side WebFetch (also performed!) missed. The discipline holds because TWO independent verifications run against the same authoritative source.

10. **"Forward-prepared CVE pins need activation pre-requisites that fit REAL corpus shape, not canonical case."** The morning session shipped 6 pins with documented activation conditions; this session activated them via 3 commits driven by end-to-end DS1 verification. Each commit closed a different gap that the prior commit missed. **Incremental gap closure via fixup commits per Rule #25 is the right shape** when corpus-shape fit isn't predictable from spec.
