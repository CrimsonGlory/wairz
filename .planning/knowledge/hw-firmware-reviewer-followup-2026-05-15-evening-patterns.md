### 4. Shared advisory_id across N entries with documented dedup behavior

- **Description:** When N curated YAML entries cover the same SPEC-level CVE cluster (e.g. FragAttacks across broadcom + qualcomm WiFi), set the SAME `advisory_id` across all N entries. The matcher dedupes per `(firmware_id, blob_id, cve_id)` UNIQUE — even if two entries matched the same blob (impossible in practice since vendor differs), one advisory row is emitted. The expected duplicate-advisory_id WARN at load time is intentional and documents the convergence.
- **Evidence:** Commit `54a0a32` shipped `ADVISORY-FRAGATTACK` (19 chars; fits VARCHAR(20)) shared across the 2 FragAttacks advisory entries. Post-rebuild verification: 32 ADVISORY-FRAGATTACK rows in the corpus (one per qualcomm wcn3xxx blob; broadcom entry fires on 0 blobs because corpus has 0 broadcom/wifi blobs). The implementer's regression canary `test_fragattacks_advisory_id_canonical_and_fits_varchar_20` pins the literal string + asserts both entries carry it.
- **Applies when:** Converting N curated CVE pins to advisory-only across N vendor-fork entries that share the same conceptual scope. Shared advisory_id preserves operator visibility on each vendor's blobs while respecting the per-vendor matching narrowing (chipset_regex, category_regex). Anti-pattern to avoid: distinct per-vendor advisory_ids when the conceptual scope is identical (loses dedup; doubles operator-facing rows for no gain).

### 5. Surgical DELETE before cve-match for YAML-edit-driven row changes

- **Description:** The matcher's `force_rescan=True` removes the dedup check but doesn't DELETE existing rows — would hit UNIQUE constraint violations on re-insert. For YAML-edit-driven row changes (curated entry conversion, version_regex addition), surgical DELETE of affected (firmware_id, cve_id) pairs BEFORE running cve-match without force_rescan is the correct shape. Companion to Pattern #9 from morning's postmortem (which addressed DETECTION re-runs; this addresses MATCHER re-runs).
- **Evidence:** This session's verification step: `DELETE FROM sbom_vulnerabilities WHERE firmware_id IN (...) AND cve_id IN ('CVE-2020-24586','CVE-2020-24587','CVE-2020-24588','CVE-2023-20819','ADVISORY-FRAGATTACK','ADVISORY-WLAN-FRAGATK')` removed 308 rows; subsequent cve-match without force_rescan inserted 32 ADVISORY-FRAGATTACK rows + preserved all baselines. No UNIQUE constraint violations.
- **Applies when:** Verifying a YAML edit that changes which CVE IDs the matcher emits on existing blob rows. Document the surgical DELETE shape in the test plan; consider whether the affected CVE list should be scoped to a single firmware corpus (verification) vs the whole DB (production rollout).

### 6. Boundary-anchored regex `(?:^|[^a-z0-9])...(?:[^a-z0-9]|$)` prevents whole-substring false-positives

- **Description:** When matching a version-family token or chipset codename that may appear as a SUBSTRING of unrelated strings (e.g. `nr15` could appear inside `nr155_else`; `lr12a` could appear inside `lr12abc`), wrap the regex's family tokens in boundary lookarounds. The character class `[^a-z0-9]` excludes `_` from "word chars" — correct for underscore-separated banner shapes like `MOLY_NR16_R1`. The `(?:^|...)` and `(...|$)` shapes handle start-of-string + end-of-string edges.
- **Evidence:** This session's CVE-2023-20819 version_regex `(?i)(?:^|[^a-z0-9])(lr11|lr12a|lr13|nr15|nr16|nr17)(?:[^a-z0-9]|$)` verified against 10 positive cases (all 6 NVD families in MOLY/bare/underscore forms) + 7 negative cases (LR18/NR18/LR12/LR14 out-of-scope + `nr155_else`/`lr12abc` confused-substring guards). All assertions passed.
- **Applies when:** Any regex matching a version/codename/family token that may legitimately appear as a substring of other tokens. Use lookarounds with `[^a-z0-9]` (case-insensitive via `(?i)`) rather than `\b` word-boundary (which fails on underscore-separated paths per Antipattern #9 from morning's postmortem).

### 7. Hard-reject `version_regex` matcher semantics are durable forward-prepared substrate

- **Description:** The cve_matcher.py:480-491 comment explicitly states "Stays STRICT — when present, version evidence MUST be found". Soft-fallback applies to `chipset_regex` only, NOT `version_regex`. This contract enables forward-prepared CVE pin shape — landing a version_regex with no extraction infrastructure today produces ZERO false-positives (hard-reject drops all blobs with NULL version), then activates the moment the parser ships. A future change of this contract (soft-fallback on `version_regex`) would silently re-introduce over-attribution.
- **Evidence:** The gate-canary test `test_cve_2023_20819_hard_rejects_blob_with_null_version` asserts the hard-reject path actually fires on NULL version. Without it, a silent semantics regression from hard-reject to soft-fallback would go undetected.
- **Applies when:** Designing a forward-prepared CVE pin OR auditing the matcher's narrowing semantics. The hard-reject contract is the load-bearing assumption — document it in YAML headers OR in `docs/features/extending-firmware-patterns.md` (Reviewer C C8 deferred). Companion to Pattern #3 above (forward-prepared CVE pin pattern depends on hard-reject semantics).

### 8. Pre-implementation corpus baseline audit + post-rebuild delta validation (Rule #31 width-canary applied to YAML edits)

- **Description:** Before any YAML-edit-driven row change, run a corpus-scoped SQL query capturing the baseline row counts for all affected CVE IDs across the verification firmware corpus. After the rebuild + cve-match cycle, re-run the same query and validate the deltas match calibration. Costs ~1 second; eliminates surprise deltas during the post-rebuild verification step.
- **Evidence:** This session's pre-rebuild SQL captured: CVE-2017-18159=147, CVE-2020-24586/87/88=96 each, CVE-2023-20819=20, CVE-2021-30348=54, Tegra 30 (11+4+11+4). Post-rebuild SQL confirmed: FragAttacks SPEC CVEs → 0; ADVISORY-FRAGATTACK → 32; CVE-2023-20819 → 0; all baselines UNCHANGED. Net delta calibrated correctly (−276 rows).
- **Applies when:** Any session that edits known_firmware.yaml in a way that changes matcher output. The pre/post baseline check is the load-bearing verification — distinguishes "matcher correctly applied new YAML" from "matcher silently regressed in some other way".

### 10. Rule #38 cwd-discipline subshell-scoped `cd` for sequential cwd-sensitive invocations

- **Description:** Bash tool's cwd persists across calls. After `cd backend && uv run pytest tests/foo.py`, subsequent `git status backend/...` resolves against `backend/backend/...` — Rule #38 antipattern. Mitigation: use subshell-scoped `( cd backend && uv run pytest ... )` so the cd doesn't leak into the next call. For git commands, use `git -C /home/dustin/code/wairz <subcommand>` (matches system prompt's explicit guidance).
- **Evidence:** Caught mid-session this session — after a `cd backend && uv run pytest` invocation drifted the cwd, the next bash command was `pwd` which surfaced `/home/dustin/code/wairz/backend`; reset to repo root via `cd /home/dustin/code/wairz && pwd` before next git command; switched to subshell `( cd /home/dustin/code/wairz/backend && uv run pytest ... )` for subsequent pytest invocations. Net 0 git-resolution errors in the commit log.
- **Applies when:** Any session with multiple Bash invocations where some need a different cwd (e.g. `uv run pytest` in `backend/`) and others need the repo root (e.g. `git -C ... <subcommand>`). Subshell-scoping is the durable shape; absolute paths everywhere else.
