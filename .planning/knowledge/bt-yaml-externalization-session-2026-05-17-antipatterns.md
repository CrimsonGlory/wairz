## Failed Patterns

### 1. Disclosure-batch attribution antipattern recurred at the DoS-CVE layer after the 2026-05-16 fixup excised only the highest-severity (RCE) member
- **What was done:** 2026-05-16 session shipped a BT firmware banner parser whose `_BRAKTOOTH_CVES` tuple contained 4 CVE IDs (28139 RCE + 34147/31609/31612 DoS). Reviewer B 2026-05-16 caught CVE-2021-28139 as ESP32-only per NVD CPE; the fixup commit `ae91e98` correctly excised it but did NOT independently verify the remaining 3 DoS CVEs against NVD CPE. Each of the 3 turned out to belong to a different vendor (Cypress, Silicon Labs, Zhuhai Jieli) per NVD.
- **Failure mode:** 216 wrong-CVE rows shipped to the wairz corpus across 5 firmwares — including the 39 banner-pin tier rows the 2026-05-16 verify script "confirmed" were Tier 0 BRAKTOOTH attribution. Each row would have produced misclassified SBOM CycloneDX VEX exports, NVD-pinned dashboard mismatches, and CPE-driven dedup errors across every downstream consumer.
- **Evidence:** Reviewer B 2026-05-17 audit; direct NVD CPE web-fetch on each of 4 CVE IDs confirmed the per-CVE vendor split.
- **How to avoid:** Per-CVE NVD-CPE verification is a RECURSIVE discipline — every CVE in a disclosure batch needs independent verification, not just the most egregious one. When a reviewer-fixup excises ONE wrongly-attributed CVE from a batch, the AUDIT must extend to every remaining CVE in the same batch with the same shape. The narrow canary test that protected CVE-2021-28139 specifically did NOT generalize — broaden to an allowlist-shape invariant ("no member of {disclosure batch's non-Qualcomm CNAs} appears under qca_rome"). Cost: ~30 sec per CVE via NVD web-fetch; eliminates the recursive-miss failure mode permanently.

### 2. Curated-YAML cascade — the same 3 wrong CVE IDs lived in `known_firmware.yaml` independent of the parser path
- **What was done:** The H2 reviewer-fixup commit (`be04f84`) corrected the 3 wrong CVE IDs in the parser-side YAML (`bt_banner_cve_pins.yaml` + `_BANNER_CVE_PIN_DEFAULTS`). I assumed the fix was complete and proceeded to Rule #8 rebuild + final verification. The corpus SQL audit revealed the 3 wrong IDs were ALSO living in the curated `known_firmware.yaml` BRAKTOOTH cluster entry, producing duplicate-shape rows via the curated_yaml matcher tier independently of the parser-pin tier.
- **Failure mode:** 123 additional wrong rows beyond the 39 banner-pin tier rows (G32: 57, G30: 48, DPCS10×3: 18). The same Reviewer B per-CVE-NVD-CPE discipline applied to a DIFFERENT YAML file that I hadn't searched.
- **Evidence:** Post-rebuild SQL audit grouped rows by `match_tier`: `parser_version_pin` had the expected post-fixup rows, but `curated_yaml` still had the pre-fixup wrong CVEs. Required a SECOND fixup commit (`cd9f218`).
- **How to avoid:** When a reviewer finding targets a SHAPE of issue ("3 CVE IDs are non-Qualcomm-CNA"), grep the WHOLE repo for the 3 CVE IDs, not just the file the reviewer cited. The discipline is "find every place the same shape of attribution lives." Mechanical detection: after applying the fixup, `grep -rn 'CVE-2021-(34147|31609|31612)' backend/` MUST return 0 hits across YAML + Python + tests + docs. Today's session ran the grep AFTER the rebuild and DB-audit, surfacing the cascade — should have run it BEFORE Rule #8 rebuild.

### 3. Soft-chipset NULL-fallback re-fires CVE-2023-28581 false positives on every re-cve-match indefinitely
- **What was done:** 2026-05-16 session retargeted CVE-2023-28581's `chipset_regex` to the actual NVD CPE list (FastConnect/QCA64xx/Snapdragon-865+) and deleted the stale wrong rows from `sbom_vulnerabilities`. But the matcher's soft-chipset NULL-fallback semantics treat NULL `blob.chipset_target` as "match with confidence downgrade" — so every qualcomm+wifi blob on G32 + G30 with NULL chipset_target RE-FIRES the CVE on every cve-match cycle.
- **Failure mode:** 32 false-positive rows reappeared post-rebuild (16 per firmware × 2 firmwares). The user's 2026-05-17 prompt explicitly noted "today's re-detect+re-cve-match cleaned G32+G30+DPCS10 but other firmwares may carry stale rows" — but DIDN'T flag that the same rows would re-appear under the soft semantics. The architectural issue meant DB cleanup alone wasn't durable.
- **Evidence:** Post-rebuild SQL audit grouped by `match_confidence` showed 16 rows per firmware at confidence=medium with chipset_target=NULL.
- **How to avoid:** When a fix targets a chipset_regex narrowing AND the matcher has soft-fallback semantics, EITHER (a) understand the soft-chipset behavior and choose between `strict_chipset` opt-in vs continued soft semantics per the CVE's CPE-list breadth, OR (b) verify post-fix that the false positives are durably gone via at least one re-cve-match cycle. The 2026-05-16 session did the DB cleanup but didn't re-cycle the matcher to confirm — today's re-cycle surfaced the regression. Add the `strict_chipset: true` opt-in for restrictive CPE entries; default false preserves the wide-coverage case.

### 4. H3 docs invoked nonexistent MCP tools in the worked example
- **What was done:** H3 Hennessy/QCA6490 worked example's Step 5 invoked `detect_hardware_firmware(project_id, firmware_id, force=True)` and `cve_match_firmware(project_id, firmware_id)` as MCP tools. Neither name exists in the registry.
- **Failure mode:** Every operator following the worked example verbatim would have hit an MCP-tool-not-found error at the most critical verification step. The docs were written from memory + reasonable guess about what the MCP tools should be named, not verified against the actual registry.
- **Evidence:** Reviewer C operator-walkthrough audit; verified via `grep -n 'name="' backend/app/ai/tools/{hardware_firmware,sbom}.py` — actual names are `analyze_hardware_firmware`, `check_firmware_cves`, `run_vulnerability_scan`, plus the cve-match REST endpoint.
- **How to avoid:** When writing operator-facing docs that include callable APIs (MCP tools, REST endpoints, SQL queries, etc.), the citation MUST come from a `grep` against the actual source-of-truth. The trust-my-memory shortcut on API surfaces is high-risk for the operator UX (the docs are the contract; if the doc says `detect_hardware_firmware`, operators try `detect_hardware_firmware` and get cryptic errors). Mechanical detection: write a docs-link-check that exercises every MCP tool name referenced in `docs/**/*.md` against the registered name list. Cost: ~30 LOC; would have caught today's HIGH severity Reviewer C finding.

### 5. Observability gap — operators couldn't tell if YAML loaded vs defaults fired
- **What was done:** Both H1 and H2 loaders shipped with INFO logs on missing-file/syntax-error fallback paths and WARN logs on structural-validation fallback paths, but NO log on the SUCCESS branch. An operator who edits a YAML, restarts the container, and expects their new pin to fire had no signal that their YAML was actually consumed vs silently fell back to defaults.
- **Failure mode:** A malformed-but-syntactically-valid YAML (e.g. typo in a chipset name) silently falls back to defaults; the operator sees no error in UI, no error in MCP output, no error in the loader log (because INFO/WARN only fire on the fallback path). The architectural issue meant "did my YAML load?" was an UN-OBSERVABLE state.
- **Evidence:** Reviewer C operator-walkthrough audit. Independently confirmed by `grep -rn "yaml\|patterns_loader\|cache_clear" backend/app/main.py` returning empty.
- **How to avoid:** Every YAML loader should emit a SUCCESS-branch log line that says (a) the file path was read, (b) N entries loaded, (c) "YAML, not defaults" explicit signal. Cheap. High-leverage. Today's H1+H2 fixup added: `bt_qca_codenames.yaml loaded — 5 codenames, 4 braktooth chipsets, 18 mtk chips (YAML, not defaults)` and similar for H2. Operator `grep -E "patterns_loader.*loaded"` returns one line per YAML per backend boot — single command, definitive signal.

### 6. format-string attribute-access reachability via operator-supplied YAML
- **What was done:** `_format_rationale` used `template.format(**vars)` on the operator-supplied `rationale:` string from `bt_banner_cve_pins.yaml`. Python's default `str.format` permits attribute-access syntax: `{banner.__class__.__mro__}` resolves to attribute lookups on the supplied string vars.
- **Failure mode:** A YAML pin authored as `rationale: "leak {banner.__class__.__mro__}"` would resolve to `"leak (<class 'str'>, <class 'object'>)"` — leaking internal object hierarchy. While the YAML files are git-reviewed today (so the risk is theoretical), the H2 design explicitly INVITES operator extension; future operator-supplied YAML (vendor uploads, fleet rollouts) inherits the attack surface.
- **Evidence:** Reviewer A 2026-05-17 finding. Verified by repro: `"leaked: {banner.__class__.__mro__}".format(banner="test")` → `"leaked: (<class 'str'>, <class 'object'>)"`.
- **How to avoid:** When a code path applies `str.format` to operator-supplied templates, default to either (a) `string.Template.safe_substitute` (only supports `$name`, naturally rejects attribute access), or (b) a custom `string.Formatter` subclass that rejects `.` and `[` in field names. Today's fix used (b) to preserve the existing `{name}` syntax. Test the rejection via canary (Rule #46) — synthesize a malicious template and assert the formatter falls back to the raw template.

### 7. Test-fixture cascade after a dataclass field addition
- **What was done:** The H2 fixup added a `signed_eq` field to `BannerCvePin`. Every existing test that constructed a `BannerCvePin` via `PL.BannerCvePin(...)` started failing on the new required field. I initially tried to repair each test in-place via per-line `signed_eq=None` additions.
- **Failure mode:** 9 test sites needed edits; per-site changes are tedious and error-prone (some sites use shorter shapes, others use longer); the per-line `replace_all` left 4 sites still broken after one pass. Each broken test produces a non-actionable error message about "missing required field" rather than the actual test intent.
- **Evidence:** Pre-factory: 4 test failures from missing `signed_eq=None`. Post-factory: zero failures.
- **How to avoid:** When a dataclass shape is likely to grow over the campaign's lifetime (banner-pin schema is the prototypical case), introduce a test-side factory function at the START of the test file: `_make_pin(**overrides) → BannerCvePin` with all field defaults set. Tests then construct pins as `_make_pin(family="qca_rome")` and adding a new field tomorrow only requires updating the factory's default dict. Today's session refactored to this pattern AFTER hitting the cascade; the same pattern applied prospectively saves the friction.

### 8. `build_id_lt: 0` accepted silently as a likely-unfilled sentinel
- **What was done:** The H2 commented-out example for CVE-2024-20017 (MediaTek WLAN) had `build_id_lt: 0` as a placeholder ("REPLACE this"). The H2 loader's first version accepted the value silently. Per Reviewer C: every real build_id is >= 0 so the gate would never fire — operator copy-pastes the example, leaves the sentinel, and the pin is effectively dead with no error.
- **Failure mode:** The operator-extension UX would have a hidden trap. Operators copy-paste from the worked examples; if a sentinel value silently produces a dead pin, the operator iterates blind on whatever other condition they think is broken.
- **Evidence:** Reviewer C finding; verified by adding `test_loader_rejects_build_id_lt_zero_sentinel` (rejects bare `build_id_lt: 0`) and `test_loader_allows_build_id_lt_zero_with_other_gate` (accepts when combined with chipset_target_in).
- **How to avoid:** When designing schema validators, identify likely-placeholder values for each field + reject them at load time unless combined with another gate. The discipline parallels the "at least one match condition" requirement (a pin with no gates fires everywhere → reject) — extend to "a pin with ONLY a sentinel-shaped gate → reject."

## Cross-Cutting Anti-pattern Themes

1. **"Disclosure-batch attribution recurses across CVE severity tiers."** Yesterday's #1 antipattern (filename-only vendor attribution) generalized to "claim-based attribution without per-claim source check." Today's antipatterns extend that observation: 2026-05-16's fix removed CVE-2021-28139 (the RCE) but left the 3 DoS CVEs from the same disclosure batch with the same misattribution shape. The discipline countermeasure is mechanical: every CVE in a batch gets independent NVD CPE verification + the canary tests use allowlist-shape invariants (broad), not specific-CVE-absence assertions (narrow).

2. **"The same wrong attribution lives in multiple YAML files."** When a CVE attribution issue is found, it lives in the FILE THE REVIEWER CITED — but also potentially in the same shape in OTHER YAML files (curated vs parser-pin vs known_firmware vs vendor-fork mirrors). Mechanical detection: `grep -rn <CVE-ID-list> backend/` MUST return 0 hits after the fix, across ALL files, before trusting "done."

3. **"DB cleanup is not durable when the matcher's soft semantics re-fire the same rows."** The 2026-05-16 session deleted stale CVE-2023-28581 rows; today's cve-match re-cycle re-fired them via soft-chipset NULL-fallback. DB cleanup is the SYMPTOM fix; the underlying matcher semantics need a per-entry opt-in flag (`strict_chipset: true`) for restrictive CPE attribution. Architectural fixes outlast operational cleanups.

4. **"Operator-facing docs that reference callable APIs MUST be `grep`-verified against the source-of-truth."** Today's H3 docs invoked 2 nonexistent MCP tools. The docs were written from reasonable-guess memory; the actual registry is authoritative. Future docs-quality discipline: any MCP tool / REST endpoint / SQL query reference in `docs/**/*.md` gets verified against the source artifact before commit.

5. **"Success-path observability is as important as failure-path observability."** Loader patterns shipped INFO/WARN on missing/malformed paths but emitted NO success-path log. The asymmetry means "did my YAML load?" is unobservable. Default discipline going forward: every data loader emits SUCCESS-branch log AND failure-branch log; operators grep one prefix to find both.

6. **"Operator-supplied templates require explicit attack-surface hardening."** The H2 `rationale:` field is operator-controlled per the design's extension intent. `str.format(**vars)` is the default Python idiom but leaks attribute access. Use `string.Template.safe_substitute` OR a custom `string.Formatter` subclass that rejects `.` and `[` in field names. Test the rejection via canary (Rule #46). The hardening is ~15 LOC; the latent attack surface scales with future operator-extension surface area.
